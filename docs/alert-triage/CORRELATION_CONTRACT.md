# Correlation Contract

Correlation is deterministic, explainable, organization-scoped, and performed before AI. It proposes cluster membership; it never asserts an attack fact or an analyst verdict.

> Phase 7.2 implementation update: exact replay and conservative same-connector/source semantic **deduplication** now complete before correlation. That deduplication restriction intentionally does not prevent the separately governed Phase 7.3 correlation rules from using corroboration across sources.

## Candidate generation

Only compare alerts with equal `org_id`, open-compatible lifecycle, and a bounded time horizon. Candidate indexes are generated by normalized shared values: user, host, source IP, destination IP, process, file hash/path, domain/URL, rule/category, and source-supplied technique. Candidate generation is an optimization; it does not imply correlation.

## Versioned score

For each candidate pair, calculate a versioned score and retain every matched signal:

| Signal | Example points | Guardrail |
| --- | ---: | --- |
| exact source identity / occurrence | dedupe path, not correlation | never creates another canonical alert |
| same file hash or strong indicator | 35 | normalized exact equality only |
| same host and user | 25 | both must be known |
| same source IP and destination/host | 20 | private/NAT IP alone is insufficient |
| same process plus host | 15 | process string alone is weak |
| same domain/URL | 15 | normalized domain, not substring |
| same rule/category | 10 | cannot meet threshold alone |
| temporal proximity | 0–20 | decays across configured window |
| independent source diversity | 10 | reward corroboration, not repeated delivery |

Suggested initial thresholds: `>= 55` eligible for automatic *proposed* cluster membership, `35–54` queued for analyst triage, `<35` remains separate. A hard rule requires at least one strong observable or two independent non-category signals. Exact/semantic dedupe occurs before this score and is recorded separately. Thresholds are configuration with a `correlation_rule_version`, not hidden constants.

## Explanation record

Each membership decision stores: candidate alert IDs, score, rule version, evaluated time window, matched normalized values (or protected references), signals/points, candidate-source diversity, decision (`ATTACHED`, `PROPOSED`, `REJECTED`, `NO_MATCH`), actor if overridden, and timestamp.

An analyst-visible explanation can therefore say: “same user `backup`, same host `workstation-01`, same source IP `198.51.100.44`, within 4 minutes; score 70 under rules v1.” It must not claim causation.

## Cluster merge / split behavior

- A cluster has stable UUID identity; alert membership has its own immutable decision history.
- An automatic attach uses deterministic ordering and locks/unique constraints so concurrent ingestion cannot produce conflicting membership.
- Merging clusters creates an auditable merge decision: survivor cluster, absorbed cluster, all reasons, scorer version, and prior memberships. Do not delete the absorbed cluster; mark it merged/closed with its successor reference.
- Splitting/reversing a false merge is an analyst action with rationale. Recalculate derived cluster metrics but retain original decision history.
- PROMOTED clusters are not auto-merged or auto-split. Any proposed change requires analyst review because it could confuse the promotion evidence boundary.

## False-merge controls

No cross-org candidates; time caps; category/rule cannot correlate alone; weak shared fields (common usernames, RFC1918/NAT addresses, generic processes) receive low/zero weight unless paired with stronger evidence; source duplicates do not inflate diversity; and explicit analyst reject/suppress feedback is measured. The LLM may summarize an already-created cluster but cannot select members or change score/priority.
